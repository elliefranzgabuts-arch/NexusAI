# NEXUS AI — Phase 1 Decision Register

**Purpose:** Track approved direction, open decisions, required evidence, security reviews, and feature gates for the Fedora Silverblue 44 desktop.

**Current status: `PHASE 1: OPEN / NOT VERIFIED`.** This register is a working-tree document, not evidence that a control is implemented or tested. Android remains paused until Phase 9 desktop validation is complete and the owner explicitly approves resuming Android work.

**Primary reference:** [Desktop Architecture and Security Blueprint](desktop-architecture.md). The repository snapshot reviewed for this register contains a small Tauri/React shell; backend, authentication, AI, persistence, and automation controls are not implemented.

## 1. Scope, status, and authorization

Status terms:

- **APPROVED DIRECTION** records project direction only; it does not establish implementation readiness.
- **PENDING / NOT VERIFIED** means no adequate evidence is recorded. **FAILED** means a required test did not pass. **NOT APPLICABLE** requires technical justification and review.
- **SECURITY REVIEW REQUIRED** and **OWNER DECISION REQUIRED** identify unresolved review/approval gates. **BLOCKED** means do not implement or enable the dependent feature.
- Keep decision approval, implementation, test evidence, security disposition, and feature authorization as separate statuses. A test pass alone is not authorization.

### Operative Phase 1 rule

Every E-01–E-15 criterion is currently mandatory for Phase 1 technical completion. The independent scope recommendation in §9 does **not** amend this rule. Any reclassification requires explicit owner approval recorded in the ledger.

- **TECHNICALLY COMPLETE** requires every mandatory E criterion to pass with reproducible evidence; required security reviews and owner decisions to be recorded; no blocker preventing the approved scope; and explicit owner approval of Phase 1 closure.
- **PARTIALLY DEFERRED / INCOMPLETE** applies when the owner records a deferral with rationale, actual date, approver, affected features, and residual risks. Deferred criteria remain **NOT VERIFIED**, dependent features stay blocked, and the phase is not technically complete.
- Completing Phase 1 never authorizes Phase 2. Phase 2 and every subsequent phase require separate explicit owner approval and their own gates. Phase completion is not feature authorization.
- Phase 2 does not automatically authorize owner authentication, private memory, or AI integration. Computer control, automation, file modification, and command execution remain blocked by their feature gates.
- Android remains blocked until Phase 9 desktop validation and explicit owner approval.

### O-08 approved threat model and proposed acceptance criteria

The owner-approved “Option A: Strong threat model” establishes the attacker scope above. It does not change the isolation decision: B remains the first OS-enforced isolation prototype candidate, C remains the required fallback if B cannot meet the requirements, and documentation-only isolation Option A remains insufficient for sensitive features. The following are **proposed engineering acceptance criteria, not verified results or a claim of universal security**. They require synthetic test data only and do not authorize real sensitive data, real personal-data workflows, sensitive endpoints, provider secrets, or computer-control workers. O-01’s approved synthetic-only Phase 1 encrypted persistence and recovery scope is unchanged.

1. **Process and memory isolation:** On the target Fedora environment, test the in-scope same-UID attacker’s ability to inspect or interfere with protected backend/worker processes, including arguments, environment, memory, and file descriptors wherever OS controls permit. Record effective controls and residual exposure; no protected secret or synthetic canary may be recovered.
2. **Desktop UI process inspection/interference:** Include partial inspection/interference with the NEXUS desktop UI process. Establish whether UI-visible or UI-extracted material can be used against protected backend operations; any extracted credential that enables unauthorized backend access fails. Complete compromise/control of the Fedora desktop session remains excluded.
3. **IPC identity and unauthorized connections:** Test endpoint discovery, connection, impersonation, and peer identity. In-scope same-UID processes must not gain access to protected IPC or sensitive handlers absent authorization; UID equality or possession of a discoverable endpoint alone is not sufficient proof of trusted NEXUS identity.
4. **Credential secrecy and replay resistance:** Test exposure and misuse of credentials, tokens, and sessions, including theft, replay, stale credentials, and credentials exposed through the UI process. Protected operations must reject unauthorized, stale, revoked, and replayed credentials; record where secrets can be observed and the effective mitigations.
5. **Filesystem and configuration integrity:** Test unauthorized read and mutation of protected synthetic files, service state, configuration, executable and IPC endpoint paths, including relevant ownership, permission, symlink, and replacement cases. Protected-file access or mutation by an in-scope attacker fails.
6. **Backend-side authorization and LOCKED enforcement:** Verify authorization at the backend for every sensitive operation, independently of UI/client claims. Unauthenticated, unauthorized, stale, revoked, or LOCKED-state requests must be rejected; no client-side restriction alone is sufficient.
7. **Worker containment:** Before any future worker authorization, test that a compromised or malicious same-UID caller cannot escape the worker boundary, access protected secrets/files, invoke unauthorized backend operations, or continue privileged work after revocation. Worker-specific evidence must satisfy the applicable P-10/E-15 gates; this decision authorizes no worker.
8. **Lifecycle and revocation:** Test backend/service restart, Fedora lock and suspend/resume transitions, session revocation, and credential rotation. Old grants and credentials must cease to authorize protected operations, and uncertainty or control failure must fail closed. Assess availability and denial-of-service behavior and record observed limits; this decision approves no availability guarantee.
9. **Repeatable evidence and independent review:** Preserve reproducible procedures, target OS/software versions, effective security configuration, synthetic fixtures, results, failures, and residual risks without recording secrets. Repeat the relevant tests and obtain independent security review before any sensitive feature is considered for approval.

**Mandatory failure conditions:** fail if an in-scope attacker recovers any protected secret or synthetic canary; accesses or mutates a protected file without authorization; causes an unauthorized sensitive operation to be accepted; reuses a stale or replayed credential successfully; extracts a credential from the UI process that enables unauthorized backend access; or encounters a required control that is missing, ineffective, or silently fails open. An inconclusive or unperformed test is **NOT VERIFIED**, never passed. Finite test results support only the behaviors and conditions actually tested; they do not prove universal security.

### O-08 owner-approved UI confidentiality boundary and proposed UI criteria

The owner selected **“Option A: Strict UI confidentiality boundary,”** treating the NEXUS desktop UI as an untrusted presentation layer. This UI-boundary option label is distinct from “Option A: Strong threat model” and from isolation Option A (documentation-only limitations). Backend encryption keys, provider secrets, and protected backend credentials must not be exposed to the UI. The UI must not possess reusable authorization capabilities that independently grant sensitive backend access. Information already rendered or made available to the UI may be exposed when an in-scope attacker inspects or interferes with the UI process. The backend must independently authenticate and authorize every sensitive request; frontend claims, button clicks, and confirmation messages are not sufficient proof of owner intent. UI compromise must not automatically grant backend access or sensitive-operation authority, and backend responses must minimize information exposed to the UI. This is an owner-approved design boundary, not implementation approval or verified security evidence.

**O-05 compatibility:** The approved strong-passphrase primary authentication direction remains unchanged. The passphrase must never be logged, persisted in frontend storage, placed in command-line arguments or environment variables, or retained unnecessarily. UI-01 addresses backend-held encryption keys, provider/service secrets, and reusable backend-access material; it does not assert that the O-05 passphrase can never enter an input component or UI-process memory transiently. Its input path must be separately designed and assessed against partial UI inspection and interference; a normal frontend password field is not automatically a trusted input mechanism. No trusted input or confirmation mechanism is currently approved or verified. Until an adequate input and owner-confirmation mechanism is designed and validated, sensitive operations requiring fresh owner authentication or confirmation remain blocked.

The following UI criteria are **PROPOSED / NOT VERIFIED**; they do not mark any E-criterion or prototype as passed:

- **UI-01:** Backend encryption keys, provider secrets, and protected backend credentials never enter UI memory, storage, environment variables, or command-line arguments.
- **UI-02:** No reusable backend authorization token or general-purpose capability is exposed to the UI.
- **UI-03:** Backend independently validates authentication, authorization, session state, and operation scope.
- **UI-04:** Forged frontend confirmations and manipulated UI requests cannot independently authorize sensitive operations.
- **UI-05:** Backend responses expose only the minimum information needed by the UI.
- **UI-06:** Partial UI inspection or interference cannot directly expose protected backend secrets or bypass backend authorization.
- **UI-07:** Information already rendered or made available to the UI is explicitly classified as potentially exposed under this threat model.
- **UI-08:** If the trusted owner-confirmation mechanism is unavailable or cannot be verified, sensitive operations fail closed.

**Mandatory UI failure conditions:** backend secrets are recoverable from the UI process; reusable authorization capabilities are extractable and usable for sensitive backend access; manipulated UI requests bypass backend authorization; frontend confirmation alone authorizes a sensitive action; unnecessary protected information is exposed by the backend; or an unavailable/unverified trusted confirmation mechanism results in silent authorization. An unperformed or inconclusive UI test remains **NOT VERIFIED**.

Foundation decisions required by E-13 include data policy, O-02, O-05, O-08, Phase 1-relevant O-09, and residual-risk dispositions. O-01 is required if sensitive persistence is in approved Phase 1 scope; otherwise record an owner-approved deferral. Face, voice, cloud categories, and notification preferences need not be decided while their features remain blocked.

### O-05 approved policy details and remaining validation

- **Failed authentication:** use progressive delays and temporary lockouts, never permanent automatic lockout, and generic error messages. Protect attempt counters using local protected storage plus OS-backed protection where feasible; failure state should survive app restarts. Rollback, tampering, same-UID, and compromised-account limits remain to be evaluated.
- **Session security:** default inactivity timeout is 5 minutes; configurable range is proposed as 1–30 minutes. Fedora lock/suspend must trigger immediate NEXUS locking. Fedora unlock does not unlock NEXUS; fresh NEXUS authentication is required. Hide protected UI, revoke elevated permissions/grants, and cancel or safely pause work.
- **Sensitive operations:** ordinary operations require an authenticated NEXUS session and applicable permissions. If separately authorized, lower-risk sensitive operations may receive narrowly scoped, short-lived grants; high-risk operations require individual fresh passphrase authentication, and high-impact operations also require explicit confirmation. Grants expire and are revoked on NEXUS lock; one approval cannot cover unrelated operations. Examples include destructive file operations, terminal commands, software installation, security changes, private-data export, and recovery, but this direction does not lift any existing feature gate or authorize arbitrary shell execution.
- **Still-unresolved safeguards:** Argon2id parameter selection and hardware benchmarking; credential-record integrity/tamper protection; counter rollback/reset resistance; O-01 recovery-material generation, encryption, storage, rotation, and restore tests; secure Tauri/backend authentication flow; same-UID/compromised-account limitations; Fedora lock/suspend revocation; operation-specific authorization enforcement; and O-02-compatible recovery. None is implemented or validated by this owner decision.

### O-10 approved direction and remaining validation

- **Security audit logs:** record only necessary security events, such as authentication success/failure, lock-state transitions, authorization denials, and recovery attempts. Avoid unnecessary personal or operational information.
- **Application diagnostics:** keep separate from security audit logs, minimize their content, and do not log passwords, authentication tokens, private prompts, conversation transcripts, or sensitive content by default.
- **Retention and access:** define retention and deletion policy; the duration and exact access mechanism remain undecided. Log access must follow NEXUS authorization/state restrictions and cannot bypass LOCKED protections.
- **Notifications:** while LOCKED, only generic information is permitted. To remain within the stricter O-02 whitelist, that means generic service availability only; personal details and private activity are excluded. Private notifications remain disabled until authorization and privacy controls are validated.
- **Gate:** this is direction approval only. Logging, retention, access control, and notification behavior remain unimplemented and unvalidated.
